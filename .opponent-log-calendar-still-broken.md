   Re-run from the same browser session, same cookies, ~3 minutes after cycle 1:

   - Same browser, same session cookie set — only difference is elapsed time since the `a3882d7` + `7292588` pushes triggered fresh Vercel deploys

2. **The PERSISTENT bug is React hydration error #418.** Still fires on every authed `/` load (re-verified, same minified frame `4bd1b696-f785427dddbba9fb.js:1:35057`). The #418 does NOT correlate with the 503; it persists in steady state.

3. **The `/` RSC payload is 643 KB on every refresh.** That's a lot to ship on every `router.refresh()`. On a slow mobile connection (Erik tested "in app and on chrome" — "in app" suggesting mobile webview), an in-flight 643 KB stream may abort, drop, or time out — and Next.js's router would treat the failure as "nothing to merge", leaving the UI stale. Hypothesis only; needs a throttled-network repro.

**Working theory updated**:
- **Cold-start 503s** are real but transient; they cause sporadic "stale-after-action" but resolve themselves within ~minutes after a deploy.
- **React #418 hydration mismatch** is the *persistent* steady-state bug. It triggers a full client-side re-render of (some part of) the tree, which means client state derived from initial RSC sticks around even after `router.refresh()` because the re-rendered subtree owns its own state machine.
- **Large RSC payload** may compound on slow networks.
