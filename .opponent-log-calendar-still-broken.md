## 2026-05-24T08:28Z — POSITIVA cycle 5: React #418 — three hydration mismatches fixed

**Goal**: chase cycle 4's lead. SSR HTML lacked attendee labels even though `EventBlock` renders them given `total > 0` and `heightPx >= 40` — implying `heightPx` evaluates differently SSR vs hydrated. Trace upstream.

**Trace**:
- `EventBlock.heightPx` = `f(startMinutes, endMinutes, hourOffsets, hourHeights)`.
- `startMinutes` / `endMinutes` go through `hourMinuteInTz(iso, userTz)`. `userTz` comes from `useUserTimezone()` which is already SSR-safe (returns 'UTC' on first render). ✓ ruled out.
- `hourOffsets` / `hourHeights` come from `computeFisheyeHeights(centerSlot)`. `centerSlot` initial state is the literal `24`. Stable. ✓ ruled out.
- BUT — adjacent state in the same component is NOT stable:
  - `WeeklyGrid.tsx:90` `useState<Date>(() => getWeekStart(new Date()))` — server's UTC clock vs client's local clock at hydration → may produce DIFFERENT week starts.
  - `WeeklyGrid.tsx:93` `useState<number>(() => { const now = new Date(); return now.getHours() * 2 + ... })` — server UTC `getHours()` vs client local `getHours()` ALWAYS differ for users outside UTC. Erik (UTC+1) and the test browser (PDT, UTC-7) both diverge from Vercel UTC.
  - `NowIndicator.tsx:16` `useState<number>(getNowMinutes)` — same pattern, hits the now-indicator position.

Each of these produces server/client divergence on the very first render → React `hydrateRoot` detects DOM mismatch → fires `#418` → discards the subtree → re-renders client-side. The discarded subtree included the `EventBlock` cells that *would* have shown attendee labels on the server, which is why SSR HTML had zero `"going"`/`"invited"` substrings but the live DOM has them.

**Fixes** (two files, three useState calls):

1. `src/components/calendar/NowIndicator.tsx` — initial `nowMinutes` set to `null` (a value both server and first-client-render produce identically). `useEffect` populates the real value on mount + starts the per-minute interval. Renders `null` (no DOM) until mount → matches server.

2. `src/components/calendar/WeeklyGrid.tsx` — initial `currentWeekStart` set to `getWeekStart(new Date(0))` (stable epoch week) and initial `currentSlot` set to `0`. A new `useEffect` updates both to viewer-local values on mount. SSR renders an empty 1970 week (no 2026 events position into it), client hydrates with the same empty 1970 week → MATCH → hydration succeeds. Post-mount, the effect re-renders with the correct week and events appear.

1. Wait for Vercel to deploy `<commit>`.
2. Reload `/` in Chrome, capture `read_console_messages` filtering for `#418`. Expect zero hits.
3. Repeat the cycle-4 dynamic test (POST RSVP → navigate → DOM updates). Expect it to still work — the fixes here don't touch useEvents.

**ROOT CAUSE FOUND** — but NOT for #418 (yet). For Erik's actual user-facing symptom ("calendar not fixed; same problem still happening"):

`src/lib/use-events.ts:28-31` had an explicit comment-documented anti-pattern:
```ts
// Intentionally do NOT sync `events` from `initialEvents` on every prop change.
// `useState(initialEvents)` seeds state once on mount; subsequent server-prop
// re-renders would otherwise wipe optimistic RSVP/edit updates before the
// user's change reaches the DB. Use `refetch` to pull fresh server state.
```

This is the consumer-side reason the prior loop's 25-site `revalidatePath` work was inert:
- Server-side fix path was complete: route → `revalidateCalendarViews()` → fresh RSC payload on next `/?_rsc=...` request.
- `router.refresh()` after mutations correctly fetched the new RSC.
- Next.js handed the new `serverEvents` prop to `<WeeklyGrid>`.
- `<WeeklyGrid>` called `useEvents(serverEvents)`.
- **`useEvents` IGNORED the new prop**. State stayed seeded from initial mount.
- ⇒ UI showed stale data until a hard reload remounted WeeklyGrid.

This is the textbook "navigate away → edit → navigate back → grid is stale" failure mode that matches Erik's report. The prior loop's `revalidatePath` fan-out was correct in principle but landed in a UI layer that throws server data away.

**The fix** (`src/lib/use-events.ts`, one `useEffect` added):
```ts
useEffect(() => {
  setEvents(initialEvents);
}, [initialEvents]);
```

Plus updated comment explaining that the original "optimistic-wipe" concern is bounded: every optimistic-update path already calls `setTimeout(refetch, 1200)`, so even if a prop sync briefly reverts an in-flight optimistic patch, the refetch ~1.2s later restores confirmed server state. End state is correct; only sub-second flicker is possible.
