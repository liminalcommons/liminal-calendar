## Initial Discovery (handed off from human session)

### Suspected root cause
`src/lib/use-events.ts` intentionally does NOT sync `events` state from `initialEvents` prop changes (lines 28–31). The create flow in `src/components/events/EventForm.tsx` (lines 512–523) does:

```ts
const res = await apiFetch('/api/events', { method: 'POST', ... });
const data = await res.json();
const newId = data.id || data.event?.id;
router.push(`/events/${newId}`);   // <-- navigates AWAY from calendar
onSuccess?.();                      // <-- only clears localStorage
```

The user lands on `/events/{newId}` (event detail), then navigates back (browser back / nav click). When the calendar `/` page re-mounts client-side, Next.js may reuse cached server-rendered HTML; even if fresh server props arrive, `useEvents` ignores them. **Manual refresh forces full reload → fresh `useState(initialEvents)` seed → event appears.**

There IS an `addEvent` path in `useEvents` (line 58) and `WeeklyGrid.handleEventCreated` (line 151) wired to `QuickCreatePopover.onCreated` (line 155). But the actual create flow goes through `/events/new` page → `EventForm`, which does NOT call back into the calendar — that linkage is broken.

### Possible fix directions (positiva should pick the smallest sufficient)
1. **`router.back()` instead of `router.push('/events/${newId}')`** after create — simplest. But: `useEvents` still won't see the new event because `initialEvents` prop is ignored.
2. **`router.refresh()` then `router.back()`** — forces server re-render of calendar with new event, but `useEvents` still ignores prop changes.
3. **Allow `useEvents` to merge new server events** (preserve optimistic edits/RSVPs by keying on id, but accept new events). Most coherent with existing architecture.
4. **`router.push('/?newEventId=X')`** with a one-shot effect on calendar mount that calls `addEvent`. Invasive.
5. **Calendar page calls `refetch` on focus / on visibility change** — Next.js soft-nav misses server re-render; this picks up the new event.
6. **Lift event store to a context** — too big for this bug.
